## 三、关键能力升级

### 3.1 Docker 化部署（飞牛OS NAS 实战）

`docker-compose.yml` 编排两个服务：

```yaml
services:
  server:
    build: ./server
    ports: ["10002:3001"]    # 宿主 10002 → 容器 3001
    env_file: env_config/.env_fnOS
    deploy:
      resources: { limits: { memory: 1G } }
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3001/api/ping"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s

  web:
    build: ./web
    ports: ["10001:80"]      # 宿主 10001 → 容器 80
    env_file: env_config/.env_fnOS
    depends_on:
      server: { condition: service_healthy }
    deploy:
      resources: { limits: { memory: 256M } }
```

**端口选择**：10001/10002（避开飞牛OS WebUI 占用的 80 + 常见 8080/5000）。
**健康检查**：基于 `/api/ping` 端点，server 起来 web 才启动（`service_healthy`）。

### 3.2 env_config 集中管理

不再让 `docker-compose.yml`、`.env`、代码里散落配置——集中到 `env_config/`：

```
.env_default   # 兜底（最低优先级）
.env_dev       # 本地开发
.env_fnOS      # 飞牛OS 生产
.env_local     # 个人本地覆盖（git 忽略，最高优先级）
```

**加载方式**：
- **Docker**：自动通过 `env_file` 注入到 `process.env`（零手动）
- **本地 dev**：`npm run dev` 通过 `scripts/load-env.js` 自动 source
- **本地 production**：`node scripts/load-env.js env_config/.env_fnOS -- node server/dist/index.js`

### 3.3 跨平台 env loader（`scripts/load-env.js`）

**之前**：`vite` / `tsx watch ...` 直接跑，env 没注入，需要手动 `source`。

**之后**：`npm run dev` 自动从 `env_config/.env_dev` 读 → 注入 → spawn 子进程。

**实现要点**：
- 纯 Node.js，**零新依赖**
- Windows / Linux / macOS 都 work
- Windows 自动解析 `.bin/vite.cmd` 路径（避免 EINVAL）
- 同时加 `node_modules/.bin` 到 PATH（兼容 `tsc` 等命令）

### 3.4 找到一个**真实的部署 bug**

**症状**：飞牛OS 上 server 容器一直 `Restarting`，web 容器 unhealthy，502 Bad Gateway。

**误判**（以下都不是真因）：
1. 以为是 `@napi-rs/canvas@1.0.6` 用了较新 CPU 指令（illegal instruction）→ 降级到 0.1.20
2. 以为是 Node 26 NAPI 9 ABI 不兼容 → 换 Node 20 alpine
3. 以为是 health check 太严 → 放宽到 30s start_period
4. 以为是 web depends_on 太严 → 改 service_started

**真因**（`sudo docker logs model-card-server` 抓到）：

```
Error: unable to determine transport target for "pino-pretty"
```

`server/src/index.ts` 写死了用 `pino-pretty` 做日志格式化，但 `pino-pretty` 在 `devDependencies`。Dockerfile 跑 `npm ci --omit=dev`，**生产环境没有 pino-pretty** → server 启动立刻 crash。

**修法**（1 行代码）：

```ts
const isDev = process.env.NODE_ENV !== 'production';
const app = Fastify({
  logger: {
    ...(isDev && { transport: { target: 'pino-pretty', ... } }),
  },
});
```

dev 用 pino-pretty（带颜色），prod 用 pino 默认 JSON（不依赖 devDep）。

**这是通用 bug，不是部署特性**——任何 production 环境都会炸。同时 cherry-pick 到 master。

### 3.5 fnOS-release 分支策略

之前用 `master` 主线 + 频繁 force-push 到 main。改成更干净的双分支：

- **`main`**：开发主线（Node 26 + canvas 最新 + pino-pretty fix）
- **`fnOS-release`**：飞牛OS 部署专用（多 `env_config/`、部署文档、复盘报告）

**fnOS-release 相对 main 的 diff**（清理后）：

```

  env_config/                    # 平台配置
  docs/fnOS-release.md          # 分支说明
  docs/部署到飞牛OS.md          # 部署步骤
  docs/部署到飞牛OS-实战复盘.md  # 踩坑复盘

```

**日常 workflow**：
```bash

docker compose up -d --build
```

## 六、复盘教训（详见 `docs/部署到飞牛OS-实战复盘.md`）

7 条核心教训：

1. **永远先看运行时错误**，不要从 build log 推断
2. **错误信息要看完整**，不要听用户转述
3. **不要陷入"按症状猜病因"**——这次的 `illegal instruction` 报告是真因误导
4. **dev vs prod 区分要在代码里就做好**（这次 pino-pretty 缺）
5. 飞牛代理别用，daemon 走国内镜像源（`docker.m.daocloud.io`）
6. 用户反馈"不能跑"时**先看状态**（`docker ps` / `logs` / `inspect`），再讨论
7. multi-step 修复要标记得失——9 个 commit 改完才发现 1 个就够
